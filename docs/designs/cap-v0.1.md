## Vision

### 10x Check
The 10x version is "everything you've ever seen, one hotkey away" — always-on auto-capture of browsing history with full archiving and semantic recall (the Rewind/mymind direction). Named and deliberately NOT pursued: it trades the sharp Pinboard wedge for a privacy-heavy always-on product. It stays vision-only.

### Platform Potential
CapKit's `ProcessingStep` pipeline is the long-term moat: opening it to third-party steps in v0.2+ turns cap from an app into the OSS capture substrate other tools build on.

## Accepted Scope (added to this plan)
- E1: Fetch the full page over the network on link capture and extract readable body text; store and FTS-index it. **What E1 adds beyond the design doc:** the design doc's v0.1 pipeline "text extraction" covered only content already in hand (selected text, og-metadata from the title fetch); E1 fetches and indexes the whole page body. Implementation route: Readability.js in an offscreen WKWebView (handles JS-heavy pages), SwiftSoup heuristics as the lightweight fallback — hence M-L, not M. Fail-soft: on extraction failure the capture keeps title/URL/selection and marks `body_status=failed` (retryable via `cap refetch`). **Fetch policy (decided in this review, question D4): on by default, disclosed in README/FAQ, settings toggle + `cap add --no-fetch` opt-out.**
- E2: Vision-framework OCR pipeline step for image captures; OCR text FTS-indexed. (Pulled forward from the design doc's v0.2 slot — see Design Doc Amendments.)
- E4: README one-line positioning ("why this instead of Linkding/Anybox?"), 10-second capture→recall demo GIF, Show HN post draft — all before the v0.1 tag.
- E5: Raycast extension (TypeScript, calls cap CLI): search captures, open result. Lives in the cap repo under `raycast/`. **Sequencing:** built after the dogfood-week gate passes; Raycast store submission waits on the CLI-name resolution (design doc Open Question 3) and store review adds calendar latency independent of build effort.

## What already exists

Greenfield repo — `docs/` and `TODOS.md` only, no code. Nothing is being rebuilt in-house
that already exists elsewhere; every infrastructure slot takes the proven option:

| Need | Reused | Not rebuilt |
|------|--------|-------------|
| Store + full-text search | GRDB + SQLite FTS5 (bm25 built in) | No custom index, no external search engine |
| CLI argument parsing | swift-argument-parser | No hand-rolled parser |
| Global hotkey | KeyboardShortcuts | No raw Carbon event-tap plumbing |
| Article extraction | Readability.js + SwiftSoup | No bespoke DOM heuristics |
| OCR | Vision framework (on-device) | No bundled OCR model |
| Background lifecycle | launchd | No custom daemon supervisor (A1) |
| Crash isolation | separate child process | No XPC service target (T1) |
| Update notification | GitHub Releases API | No appcast, no Sparkle (TD2) |
| Distribution | GitHub Releases + Homebrew tap + notarytool | No custom installer or updater |
| Tests | Swift Testing (bundled with the toolchain) | No third-party test framework |

The one place cap deliberately does its own thing is X1's tab-first extraction — and that
exists precisely because the standard approach (refetch the URL as an anonymous client)
fails on logged-in and paywalled content. **[EUREKA]** The conventional pipeline shape is
"capture the URL, enrich later from the network." For a local-first tool running on the
user's own machine, the browser tab is a strictly better source than the network, and it's
already open. Enrich-at-capture beats enrich-later here, which inverts the usual advice.

## Failure modes

| Codepath | Realistic production failure | Test? | Error handling? | User sees? |
|---|---|---|---|---|
| Tab extraction (X1) | AppleScript JS execution denied or returns empty on a given browser | yes (per-browser matrix) | yes — falls back to network fetch | body_source='fetch', silent by design |
| Network fetch (E1) | Paywall/login wall returns a sign-in page as "body" | partial — golden corpus can't cover it | `thin` status | badge + `cap refetch` |
| Agent (A1) | LaunchAgent unloaded; queue never drains | yes | yes — `cap status` exit 4, `cap doctor` reinstalls | yes, if they look |
| Agent crash mid-fetch (T1) | WebKit crashes on a hostile page | yes (SIGKILL test) | yes — child-process isolation + startup reclaim | recovers silently |
| ⌘C fallback (A2) | Clipboard holds a file promise | yes (unit) | yes — refuses, captures link-only | yes, HUD explains |
| Secure input (A3/TD5) | Password captured from a web login form | yes (AX subrole unit) | yes — refuses | yes, HUD explains |
| AX grant (TD1) | TCC revoked by a signature change | yes | yes — re-grant prompt | yes, prompt + degraded icon |
| Store (C2) | Two processes write simultaneously | yes (two-process WAL test) | yes — WAL + busy_timeout | no, invisible by design |
| Search (TD4) | Malformed FTS query (`"`, bare `AND`, `*`) | yes (parameterized) | yes — never throws | empty results, not an error |
| Bulk enqueue (P1) | 500 URLs piped into `cap add -` | yes (50-URL burst) | yes — concurrency cap 3/1 | `cap status` shows queue + ETA |
| Dedupe (X4) | Same URL captured twice | yes (URL normalization unit) | yes — merge, don't insert | yes, "already captured 3w ago" |

**Critical gaps (no test AND no error handling AND silent): none.** The T1 stale-`fetching`
row was the one critical gap found; it is now closed by startup reclamation plus
child-process isolation.

## Worktree parallelization strategy

| Step | Modules touched | Depends on |
|------|----------------|------------|
| S1 CapKit foundation — Store, migrations, Models, schema | `CapKit/Store`, `CapKit/Models` | — |
| S2 SearchService — parsing, bm25, snippets, filters | `CapKit/Search` | S1 |
| S3 CaptureService — ingest, guards, classification, dedupe | `CapKit/Capture` | S1 |
| S4 Pipeline + agent — actor queue, WebKit child proc, OCR | `CapKit/Pipeline`, `CapAgent/` | S1, S3 |
| S5 CapCLI — commands, `--json`/tsv, exit codes, stdin | `CapCLI/` | S2, S3 |
| S6 CapApp — hotkey, HUD, search window, onboarding, TCC | `CapApp/` | S2, S3 |
| S7 Release CI — universal build, signing, notarize, tap | `.github/`, `Package.swift` | — |
| S8 Raycast extension | `raycast/` | S5 |

```
Lane A: S1 → S3 → S4          (sequential, shared CapKit internals)
Lane B: S2                     (after S1; independent module)
Lane C: S7                     (independent from day one — start with a hello-world binary)
Lane D: S5 → S8                (after S2 + S3)
Lane E: S6                     (after S2 + S3)
```

**Execution order:** S1 alone first — everything blocks on the schema. Then launch Lane B (S2)
and Lane C (S7) in parallel while Lane A continues into S3. Once S2 and S3 land, Lane D and
Lane E run in parallel worktrees. S7 runs the entire time, independent of all of it.

**Conflict flags:** S3 and S4 both touch CapKit internals and both call into Store — keep them
in the same lane, sequential. S5 and S6 both consume `SearchService` and `CaptureService` but
own separate target directories, so they parallelize cleanly. S7 touches `Package.swift`, which
S1 also creates — start S7 only after S1's manifest exists.
